 13Liveness
 14========
 15
 16## Status
 17
 18Currently liveness tracking only tracks local variables in functions.
 19
 20In particular it doesn't handle:
 21
 22* PHI temporaries
 23* Variables that aren't constructed via IRVar
 24* Variables that might be introduced via slang-ir-restructure-scoping.h/.cpp
 25* Possible variable 'escape' via pointers (shouldn't be possible right now - but restructuring might
 26introduce issues)
 27* Any tracking around undefined values
 28
 29If enabled output source will output with SLANG_LIVE_START and SLANG_LIVE_END macros. It's a user
 30space problem as to how to use these definitions (for example by adding a prelude).
 31
 32## Motivation
 33
 34At a first approximation liveness means variable is `in scope`. The underlying issue might be
 35described as
 36
 37```HLSL
 38struct SomeStruct
 39{
 40    int value;
 41    int large[100];
 42};
 43
 44int someFunction()
 45{
 46    int result = 0;
 47
 48    for (int i = 0; i < ...; ++i)
 49    {
 50        doSomething();
 51
 52        SomeStruct s;
 53        s.value = ...;
 54
 55        doSomethingElse(s);
 56
 57        result += s.value;
 58    }
 59
 60    return result;
 61}
 62```
 63
 64A compiler might hoist `s` outside of the loop, looking something more like...
 65
 66```
 67int someFunction()
 68{
 69    SomeStruct s;
 70    int result = 0;
 71
 72    for (int i = 0; i < ...; ++i)
 73    {
 74        doSomething();
 75
 76        s.value = ...;
 77
 78        result += doSomethingElse(s);
 79    }
 80
 81    return result;
 82}
 83```
 84
 85The problem is that now `s` is in scope over the loop, and there is potential for values from one
 86interation to be used in the next iteration. This isn't a problem in the original version because it
 87is 'obvious' that a new `s` is constructed each iteration. The key observation being that when
 88doSomething is executing, `s` doesn't exist, and so doesn't need to take any register space.
 89
 90Why hoist? Some compilers define variables via `alloca`s, and these allocas can only be placed at
 91the start of the function. That being the case their scoping for where the contents is 'live' is
 92lost.
 93
 94So liveness here is adding additional information about variables use. The start of the range is
 95where there is a 'fresh' copy of the variable, and the end is where where the values held in the
 96variable can no longer alter execution results.
 97
 98## Discussion
 99
 100The previous discussion of liveness could be described as being at the 'variable' level.
 101
 102Liveness could be tracked in a more fine grain manner - such as tracking field liveness. `s` has no
 103`__init` and isn't initialized in any way. s.value does set some state, but `large` is untouched. So
 104in a sense s.value holds *all* of the state of s at that point, and only s.value would need to be
 105stored to reconstruct s (the rest could be undefined).
 106
 107Is this more nuanced information useful to a downstream compilation? Maybe, but the downstream
 108compiler could perform all the same analysis. All it's really missing is knowing when there is a
 109`fresh version` of s.
 110
 111How does this apply to undefined values?
 112
 113```
 114int someFunction()
 115{
 116    int result = 0;
 117    int v;        /// v's value is undefined
 118
 119    for (int i = 0; i < ...; ++i)
 120    {
 121        doSomething();
 122
 123        SomeStruct s;
 124        s.value = v;
 125
 126        result += doSomethingElse(s);
 127    }
 128
 129    return result;
 130}
 131```
 132
 133In this somewhat silly example, s.value is set to an undefined value. At one level you could say
 134that s is *all* in an undefined state, and therefore s is stateless. That's not quite right though
 135because although v is undefined, it should probably be the same value every loop.
 136
 137Like before though, this may not matter too much in practice because a downstream compiler can see
 138this behavior, and handle appropriately.
 139
 140Another way a compiler could `see` that it has a `fresh copy` within the loop, would be for all it's
 141state to be set.
 142
 143```
 144int someFunction()
 145{
 146    SomeStruct s;
 147
 148    int result = 0;
 149
 150    for (int i = 0; i < ...; ++i)
 151    {
 152        doSomething();
 153
 154        // (Note the syntax here is not Slang/HLSL, it's just meant to mean 'initialize s')
 155        s = SomeStruct{};
 156
 157        s.value = v;
 158
 159        result += doSomethingElse(s);
 160    }
 161
 162    return result;
 163}
 164```
 165
 166Here because of the initialization of *all* of `s`, a downstream compiler can infer that during
 167`doSomething` it doesn't have to potentially store the contents of `s` because it will be wiped out
 168after the function.
 169
 170All of this gets more complex around branches. But again that is something a downstream compiler can
 171track if it has a way of knowing when a variable is in scope. Similarly calling into a function
 172could return a struct that contains fields which aren't set - this is something a downstream
 173compiler could determine when fully specialized.
 174*/
