      14                         : // An instruction that conditionally computes a resource value, such as a `select` instruction,
      15                         : // is valid in Slang IR. Several compilation targets, particularly Vulkan SPIR-V, cannot directly
      16                         : // represent all such instructions. For example, eliminating a resource-valued block parameter
      17                         : // can require a local texture or sampler variable, which Khronos targets cannot represent.
      18                         : //
      19                         : // This file implements `specializeResourceSelections`, a pass that attempts to eliminate
      20                         : // instructions that conditionally compute resources by moving the conditional computation to:
      21                         : //
      22                         : // - An index into a resource array or descriptor heap, allowing one resource access afterward.
      23                         : // - A branch around each of several resource-using operations, each using a concrete resource,
      24                         : //   allowing only their non-resource results to be merged afterward.
      25                         : //
      26                         : // Consider this example:
      27                         : //
      28                         : //     Texture2D<float4> textures[8];
      29                         : //     Texture2D<float4> other;
      30                         : //     SamplerState sampler;
      31                         : //     float4 f(bool useArray, uint i, float2 uv)
      32                         : //     {
      33                         : //         Texture2D<float4> t = useArray ? textures[i] : other;
      34                         : //         return t.SampleLevel(sampler, uv, 0);
      35                         : //     }
      36                         : //
      37                         : // We introduce the term *reconstruction recipe* for a description of how to materialize one of
      38                         : // the possible resource values. A recipe records fixed inputs, such as the array `textures`,
      39                         : // and how to use them. Inputs computed during shader execution, such as `i`, are supplied
      40                         : // separately as *payload values*. The recipe records the types of those inputs so that the
      41                         : // compiler can carry a payload for each possible recipe through the program's control flow.
      42                         : // Payloads contain ordinary values, such as integer indices or vector coordinates, whose types
      43                         : // the target can store without needing resource storage.
      44                         : //
      45                         : // For `t` above, one recipe indexes `textures` and needs the index `i` as its payload. A second
      46                         : // recipe refers directly to `other` and needs no payload. Instead of computing a selected
      47                         : // texture, we compute a *selector* that identifies the chosen recipe and carry the corresponding
      48                         : // payload values. At the `SampleLevel` operation, we branch on that selector, materialize the
      49                         : // resource for the chosen recipe, and perform the sample. Only the ordinary `float4` result
      50                         : // crosses the merge. We neither access an unselected resource nor move the sample before its
      51                         : // coordinates have been computed.
      52                         : //
      53                         : // As another example, consider this alternative input function:
      54                         : //
      55                         : //     Texture2D<float4> textures[8];
      56                         : //     SamplerState sampler;
      57                         : //     float4 f(bool useFirst, uint i, uint j, float2 uv)
      58                         : //     {
      59                         : //         Texture2D<float4> t = useFirst ? textures[i] : textures[j];
      60                         : //         return t.SampleLevel(sampler, uv, 0);
      61                         : //     }
      62                         : //
      63                         : // Both possible values of `t` can use one recipe: index `textures` using the supplied payload.
      64                         : // We select `i` or `j` as that payload, then access `textures[useFirst ? i : j]` and sample it
      65                         : // without introducing a branch around the sample. We call this case the *same-array optimization*.
      66                         : // A descriptor-heap load can use the same approach: the heap declaration is fixed, and we select
      67                         : // the descriptor index to supply as payload.
      68                         : //
      69                         : // We call an instruction that constructs a resource value or an address into its contents a
      70                         : // *resource constructor*. Examples include array access, descriptor-heap loading, and combining
      71                         : // a texture with a sampler. The recipe for such a combination contains separate child recipes
      72                         : // for the texture and sampler. A resource or array that is already available at the eventual
      73                         : // operation, such as a global shader parameter or a resource-valued function parameter, is a
      74                         : // *root*: its recipe refers to that existing IR value directly. A precombined texture/sampler
      75                         : // binding is a root too; we do not invent separately addressable bindings for its components.
      76                         : //
      77                         : // A *terminal consumer* is an instruction that uses a resource or resource-backed address and
      78                         : // produces an ordinary result, or only a side effect. Samples, memory operations, and calls
      79                         : // returning ordinary values are examples. A resource constructor is not a terminal consumer:
      80                         : // we follow its result to the operation that will use the constructed value. In particular,
      81                         : // combined texture/sampler construction must be followed through to the sample operation.
      82                         : //
      83                         : // SSA construction represents conditional resource computations as `IRSelect` instructions or
      84                         : // non-entry block parameters whose incoming branch arguments supply the possible resource values.
      85                         : // We call the connected set of those instructions, their resource constructors, and roots a
      86                         : // *selection graph*. We follow incoming dependencies and the uses of values that will be replaced,
      87                         : // so shared resource computations are rewritten together. Roots remain available and can be inputs
      88                         : // to separate graphs. A loop can introduce cycles through block parameters in a graph.
      89                         : //
      90                         : // The implementation has four phases: discover a selection graph, determine its finite recipe
      91                         : // alternatives and validate the constructions needed by its consumers, replace resource-valued
      92                         : // state with ordinary selectors and payloads, and rewrite terminal consumers. Selects and block
      93                         : // parameters belong to the selection graph, not the recipes. We can therefore represent a loop
      94                         : // with ordinary state instead of recursively expanding a resource expression. Replacement block
      95                         : // parameters exist before we construct any back-edge argument. Two recipe alternatives can use
      96                         : // Boolean state and an `if`/`else`; larger sets use integer state and a `switch`.
      97                         : //
      98                         : // Graph discovery avoids revisiting shared values, and recipe interning shares repeated
      99                         : // construction descriptions. Neither limits combinations of independent resource choices.
     100                         : // We enumerate a constructor's child-recipe combinations during analysis and again when building
     101                         : // its selector and payloads. `emitConsumer` separately enumerates combinations of the operation's
     102                         : // distinct resource arguments.
     103                         : //
     104                         : // This pass consumes late target IR. `stripAutoDiffDecorations`, also called by
     105                         : // `finalizeAutoDiffPass`, removes annotations such as `IRBackwardDerivativePrimalReturnDecoration`,
     106                         : // and `removeWeakUseInsts` removes module-level weak uses before resource specialization.
     107                         : // The live producers of `kIROp_DependsOnDecoration` attach function metadata referencing globals.
     108                         : // The entry contract excludes nonlocal references to removable resource values and external users
     109                         : // of their owned metadata. Decoration operands are exempt from ordinary IR visibility checks,
     110                         : // so this locality is a pipeline precondition, not a consequence of SSA dominance.
