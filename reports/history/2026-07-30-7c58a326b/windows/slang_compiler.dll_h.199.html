 33/// A dictionary of modules to be considered when resolving `import`s,
 34/// beyond those that would normally be found through a `Linkage`.
 35///
 36/// Checking of an `import` declaration will bottleneck through
 37/// `Linkage::findOrImportModule`, which would usually just check for
 38/// any module that had been previously loaded into the same `Linkage`
 39/// (e.g., by a call to `Linkage::loadModule()`).
 40///
 41/// In the case where compilation is being done through an
 42/// explicit `FrontEndCompileRequest` or `EndToEndCompileRequest`,
 43/// the modules being compiled by that request do not get added to
 44/// the surrounding `Linkage`.
 45///
 46/// There is a corner case when an explicit compile request has
 47/// multiple `TranslationUnitRequest`s, because the user (reasonably)
 48/// expects that if they compile `A.slang` and `B.slang` as two
 49/// distinct translation units in the same compile request, then
 50/// an `import B` inside of `A.slang` should resolve to reference
 51/// the code of `B.slang`. But because neither `A` nor `B` gets
 52/// added to the `Linkage`, and the `Linkage` is what usually
 53/// determines what is or isn't loaded, that intuition will
 54/// be wrong, without a bit of help.
 55///
 56/// The `LoadedModuleDictionary` is thus filled in by a
 57/// `FrontEndCompileRequest` to collect the modules it is compiling,
 58/// so that they can cross-reference one another (albeit with
 59/// a current implementation restriction that modules in the
 60/// request can only `import` those earlier in the request...).
 61///
 62/// The dictionary then gets passed around between nearly all of
 63/// the operations that deal with loading modules, to make sure
 64/// that they can detect a previously loaded module.
 65///
 66typedef Dictionary<Name*, Module*> LoadedModuleDictionary;
