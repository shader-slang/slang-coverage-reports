      10                         : // This file implements a pass on the IR to make the "active mask" concept
      11                         : // from HLSL explicit in the code, so that we can generate code for
      12                         : // targets like CUDA where explicit masks are used for warp-/wave-level
      13                         : // collective operations.
      14                         : //
      15                         : // At the time this pass was written, the exact semantics of the implicit
      16                         : // active mask in HLSL (and GLSL/SPIR-V) had not been specified, so this
      17                         : // file had to define what the semantics ought to be.
      18                         : //
      19                         : // The main guideline for these semantics is that it should conform to
      20                         : // the user's view of control flow based on the high-level language.
      21                         : //
      22                         : // The intuitive version of the semantics provided by this pass are:
      23                         : //
      24                         : // * Code is conceptually executed by "shards" of threads/lanes, where
      25                         : //   each shard consists of a subset of the threads/lanes in the warp/wave
      26                         : //   that are executing "together."
      27                         : //
      28                         : // * When a shard encounters a structured control-flow statement, the
      29                         : //   shard may fragment into sub-shards that partition its set of threads/lanes.
      30                         : //   E.g. for a two-way `if` we end up with a sub-shard for threads/lanes
      31                         : //   where the condition was `true`, and another sub-shard for the
      32                         : //   threads/lanes where the condition was `false`.
      33                         : //
      34                         : // * When the threads in a shard exit some structured control-flow
      35                         : //   statement normally (e.g., execution reaches the end of the "then"
      36                         : //   statement for an `if`), those threads *re-converge* with all the other
      37                         : //   threads that entered the structured statement together and which
      38                         : //   exited normally.
      39                         : //
      40                         : // * When threads in a shard exit some structured control-flow statement
      41                         : //   "abnormally" (bypassing the statements that logically come after),
      42                         : //   those threads do *not* re-converge with the other threads that exited
      43                         : //   normally, although they may still re-converge at the normal exit of
      44                         : //   some lexically outer statement.
      45                         : //
      46                         : // Turning these rules into something formal mostly comes down to codifying:
      47                         : //
      48                         : // 1. when threads exit a structured control flow statement, and
      49                         : // 2. which of those exits are "normal" vs. "abnormal."
      50                         : //
      51                         : // The Slang IR maintains structure information in its IR (similar to the
      52                         : // information maintained by SPIR-V for Vulkan). For a structured control
      53                         : // flow statement like an `if`, the IR-level representation encodes both
      54                         : // the conditional branch for the `if`, but also the label/block representing
      55                         : // the code that logically comes after the `if` in the high-level-language
      56                         : // code. We can refer to a block like that as a "merge point."
      57                         : //
      58                         : // Our more formal divergence and re-convergence behavior then depends
      59                         : // on two definitions:
      60                         : //
      61                         : // 1. Code is "inside" a control-flow structure if it is dominated by
      62                         : // the entry block, but not dominated by the merge block. Control flow
      63                         : // thus exits the structure whenever it branchs from a block inside the
      64                         : // structure to some place not inside the structure.
      65                         : //
      66                         : // 2. An edge that exits a control-flow structure represents a "normal"
      67                         : // exit if it branches to the merge block for the structure, and an
      68                         : // "abnormal" exit otherwise.
      69                         : //
      70                         : // These definitions result in divergence and re-convergence behavior
      71                         : // that closely matches what programmers expect from their high-level
      72                         : // language code.
      73                         : //
      74                         : // (Note: because the definition of what code is inside a control-flow
      75                         : // structure depends on dominance in the CFG, the existence of arbitrary
      76                         : // `goto` operations that can jump "into" a control-flow statement would
      77                         : // break our assumptions. This pass would only be compatible with
      78                         : // `goto` operations that jump "out" of control-flow statements.)
