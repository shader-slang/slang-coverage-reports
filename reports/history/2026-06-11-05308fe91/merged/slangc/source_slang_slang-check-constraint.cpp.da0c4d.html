       4                         : // This file provides the core services for creating and solving constraint
       5                         : // systems during semantic checking. Those services are used most visibly by
       6                         : // generic application solving: the generic constraint solver builds the full
       7                         : // argument list for a generic application and forms a valid `DeclRef` to the
       8                         : // generic declaration with solved type, value, and witness arguments.
       9                         : //
      10                         : // Generic argument model
      11                         : // ----------------------
      12                         : //
      13                         : // A generic application's serialized argument list is made of ordinary arguments
      14                         : // followed by witness arguments. Ordinary arguments correspond to source
      15                         : // type/value parameters that user code can name in a generic application, such
      16                         : // as `T`, `U`, `let N`, or `each Ts`. Witness arguments correspond to source
      17                         : // generic constraints, such as `T : IFoo` or `U : IData`; they are
      18                         : // compiler-formed proof values that the final decl-ref carries beside the
      19                         : // ordinary arguments.
      20                         : //
      21                         : // Before solving, `getDefaultSubstitutionArgs()` provides default substitution
      22                         : // arguments for the whole list. These are the declaration's own substitution
      23                         : // values, such as `T`, `N`, or the declared witness for `T : IFoo`. They keep
      24                         : // dependent values like `T.Value` structurally valid while the solver is finding
      25                         : // answers. The solver's live argument list is the current `m_args` array: it
      26                         : // starts from those default substitution arguments and is updated in place as
      27                         : // ordinary arguments and witness arguments become known.
      28                         : //
      29                         : // The solver has two phases. The setup phase initializes the live argument list
      30                         : // and gathers solver constraints from ordinary constraints discovered by
      31                         : // unification, default generic arguments, and source generic constraints that
      32                         : // require witness arguments. Caller-provided ordinary arguments are installed
      33                         : // into the initialized live argument list before solving starts. The resolution
      34                         : // phase runs one iterative work-list loop over the collected constraints.
      35                         : // Keeping ordinary and witness work in the same loop is the important property:
      36                         : // an ordinary argument can unblock a witness, a witness can unblock a dependent
      37                         : // default, and solving a witness can discover more ordinary constraints through
      38                         : // unification.
      39                         : //
      40                         : // Work-list states and invariants
      41                         : // -------------------------------
      42                         : //
      43                         : // A solver constraint is `Done` when it is satisfied under the current live
      44                         : // argument list, `MadeProgress` when it just changed that list, `Blocked` when
      45                         : // it is waiting for another ordinary or witness argument, and `Failed` when the
      46                         : // generic application is not viable. Progress wakes dependent work
      47                         : // conservatively; exact wake-up precision is an optimization, not part of the
      48                         : // semantic contract. A blocked constraint remains unsatisfied, so if the queue
      49                         : // becomes empty while blocked work remains, the solver rejects the candidate
      50                         : // instead of looping. Repeated retries do not count as progress by themselves:
      51                         : // a handler that computes the same answer reports `Done`, and newly discovered
      52                         : // unification facts are drained into the same work table instead of reusing a
      53                         : // separate "types first, witnesses later" pass.
      54                         : //
      55                         : // To understand how the pieces fit together, consider this code:
      56                         : //
      57                         : //      interface IData {}
      58                         : //      struct IntData : IData {}
      59                         : //
      60                         : //      interface IFoo
      61                         : //      {
      62                         : //          associatedtype Value : IData;
      63                         : //      }
      64                         : //
      65                         : //      struct ConcreteFoo : IFoo
      66                         : //      {
      67                         : //          typealias Value = IntData;
      68                         : //      }
      69                         : //
      70                         : //      U load<T : IFoo, U : IData = T.Value>(T value);
      71                         : //
      72                         : //      void check(ConcreteFoo foo)
      73                         : //      {
      74                         : //          load(foo);
      75                         : //      }
      76                         : //
      77                         : // To check `load(foo)`, the compiler must form a decl-ref for `load` as if the
      78                         : // program had written the full generic argument list. The value-level call first
      79                         : // compares the actual argument type `ConcreteFoo` with the parameter type `T`.
      80                         : // That comparison is unification: it asks what must be true for two semantic
      81                         : // values to agree. Here unification discovers the ordinary solver constraint
      82                         : // `T = ConcreteFoo`. In more structured cases, such as comparing `vector<T, 3>`
      83                         : // with a scalar argument, unification may look through promotions and nested
      84                         : // types before it discovers the ordinary constraints.
      85                         : //
      86                         : // Collection for this call produces four pieces of work: `T = ConcreteFoo`, the
      87                         : // declaration-time default `U = T.Value`, the witness constraint for `T : IFoo`,
      88                         : // and the witness constraint for `U : IData`. The default for `U` cannot be
      89                         : // substituted yet because the associated-type lookup needs both the ordinary
      90                         : // argument `T` and the witness that proves `T : IFoo`.
      91                         : //
      92                         : // The work list can solve `T = ConcreteFoo` immediately, then ask the subtype
      93                         : // system for the witness proving `ConcreteFoo : IFoo`. With that proof stored in
      94                         : // the same live argument list, substituting the default `U = T.Value` can reduce
      95                         : // the lookup to `ConcreteFoo.Value`, which is `IntData`. The solver stores
      96                         : // `IntData` as the ordinary argument for `U`, and the witness constraint for
      97                         : // `U : IData` can then prove `IntData : IData`.
      98                         : //
      99                         : // Unification can also occur while solving witness constraints. If a source
     100                         : // constraint requires `T : IBox<U>` and the solved subject is known to conform to
     101                         : // `IBox<IntData>`, solving that witness compares the required interface shape
     102                         : // with the actual conformance shape. That comparison discovers `U = IntData` as
     103                         : // a new ordinary solver constraint. The solver drains that discovered constraint
     104                         : // into the same work list so the final decl-ref is built from one coherent live
     105                         : // argument list: ordinary arguments first, followed by the witness arguments
     106                         : // that prove the source generic constraints.
