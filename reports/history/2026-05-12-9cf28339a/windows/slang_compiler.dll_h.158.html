 2#define SLANG_LLVM_BUILDER_H

 4// The LLVM target of Slang is split in two halves:
 5// * slang/slang-emit-llvm.cpp (Emitter)
 6// * slang-llvm/slang-llvm-builder.cpp (Builder)
 7//
 8// The Emitter handles all matters related to Slang IR, calling into Builder
 9// once it knows what it wants to emit. The Builder handles generating LLVM IR
 10// without knowledge of Slang IR or any other Slang internals.
 11//
 12// This split is done for a couple of reasons. First, the Slang compiler where
 13// Emitter resides, cannot directly link to LLVM. Instead, LLVM is linked to
 14// a separate and optional shared library, `slang-llvm.dll`. This is because as
 15// a dependency, LLVM is big (hundreds of megabytes) and hairy (can require
 16// compiler flags that we don't want for the compiler code). Many (or most) of
 17// the users of the Slang compiler have no need for LLVM.
 18//
 19// Secondly, this allows `slang-compiler` and `slang-llvm` to be somewhat
 20// independent; one can update the LLVM version of the Builder in `slang-llvm`
 21// without needing to recompile `slang-compiler`. It is also possible to add
 22// support for new instructions to the Emitter without having to recompile
 23// `slang-llvm`.
 24//
 25// When deciding on which side to place new code, consider:
 26// * Access to Slang IR or other matters internal to the compiler belong in Emitter.
 27// * Access to LLVM IRBuilder and code generation belong to Builder.
 28// * Builder should not be tied to Slang language concepts, but it should
 29//   cover general GPU concepts (e.g. buffers, textures etc.).
 30//
 31// A general rule of thumb is: you should be able to use Builder to generate
 32// code for _any_ GPU-targeting language, not just what Slang currently is. Even
 33// though the LLVM target only considers CPUs for now, this may not always be
 34// the case in the future, so it's good to retain the option to also emit
 35// GPU-specific things correctly.
